# 实施计划：变量与角色引用 id 化（2026-09-16）

对应需求：新增 FR-21（v0.7 立项，`docs/requirements.md` 现有最大编号为 FR-20）。
背景：变量与角色在全系统按**名字字符串**被引用（`DialogueLine.speaker`、`Choice.conditions` /
`Choice.variableEffects`、`Ending.conditions` / `Ending.variableConditions[].variableName`、
`SystemFunction.variablesRead/Write`）。后果：同名角色/变量在求值层必然合并；改名靠
`lib/store/rename.ts` 做字符串级级联（commit 81d9a4b 的止血方案）。目标是根治——引用以 id 为准，
名字只是展示。

## 事实基线补充（读代码时发现、任务书未列的关键事实）

1. `conditions` 语法只支持 `varName op value`（op 六种）+ `&&`/`||` + 括号任意嵌套（`lib/conditions.ts` 递归下降 `splitTopLevel`）；**不支持 `AND`/`OR`**，而种子脚本 `scripts/gen-witness.mjs:1017` 就写了 `conviction>=6 AND courage==true`，被当作不可解析 → 恒真。
2. `Choice.conditions` **在整个应用层没有任何手动编辑 UI**，只由 AI 写入（`app/project/[id]/structure/useBranchGeneration.ts:136`、`app/project/[id]/structure/targetedFix.ts:220,240`）。作者唯一能手填的"条件"是节点级 `systemFunction.requirements`（纯自由文本，不参与求值）。
3. `Ending.conditions` 确实被机器解析，但**只在校验引擎**（`lib/validation/engine.ts:281,430`）。预览层完全不读结局条件，结局命中纯靠 `node.type==='ending'` + 图遍历（`app/project/[id]/preview/page.tsx:188-190`）。`Ending.variableConditions` **没有任何写入 UI**（`EndingsSection.tsx` 只渲染 `conditions` 自由文本框），只被种子/脚本填充，是死字段。
4. `migrations.ts` 机制：`MIGRATIONS` 为空表、`CURRENT_SCHEMA_VERSION=1`；`migrateProject` 已是**唯一漏斗**，4 处调用（读路径 `lib/db/projects.ts:139` 的 `fromRows`；写路径 `app/api/projects/route.ts:33` 与 `app/api/projects/[id]/route.ts:55,99`；导入脚本 `scripts/migrate-json-to-db.mjs:47`），读路径惰性迁移**不写回 DB**。
5. AI 契约现状：`lib/ai/schemas.ts:150-154` 的 `speaker` 是裸 `z.string()`，不校验是否在角色清单内；`ChoiceDraftSchema.conditions/variableEffects` 是 optional string；变量喂给 AI 只有名字拼串（`lib/ai/prompts/branches.ts:9` `varNames`），不喂 id / type / defaultValue。
6. **节点 id 已经在喂 AI 并要求原样回传**（`lib/ai/prompts/branches.ts:231`、`prompts/structure.ts:372`），客户端已有 id→标题双通道兜底解析（`targetedFix.ts:55-75` `resolveRef`、`useBranchGeneration.ts:98-115` `resolveTargetId`）——id 化在本仓库已有成熟先例可照抄。
7. **`setVariables` / `setCharacters` 整表换新 nanoid**（`app/project/[id]/world/useWorldAi.ts:83` 与 `:63`，落到 `lib/store/projectStore.ts:582,267`）：点一次「AI 建议变量」就会让全项目 varId 集体悬空。这是 id 参照层的最大单点威胁。
8. **字符串级改名实测不可靠**（本次用 `rename.ts` 原函数验证）：`renameInExpr('note==trust','trust','faith')` → `'note==faith'`（右值被改）；`'mood==calm && calm>=1'` 改 `calm→serene` → `'mood==serene && serene>=1'`。止血方案不可能做对。
9. 无 `removeVariable` / `deleteVariable` action，变量只能加不能删；`addVariable`（`projectStore.ts:561`）与 `addCharacter`（`:238`）都无重名校验，可产生多个同名条目。
10. 存量真实数据反常：`data/projects/g120MnzS.json` 41 节点 / 261 行对白 / 20 个说话人**全部不在 characters（该项目 characters 为空）**；58 个选项里 23 个有 `variableEffects` 而 `variables` 为空。**迁移的主流场景是"解析不到"，不是"个别解析不到"。**
11. `public/director-run/final-project.json`：角色名 `无名来电者（'M'）` vs 对白 speaker `无名来电者（M）`——只差一对引号的近重名，任何归一化也拉不到一起，自动创建角色会凭空多出一个。
12. **仓库有测试**：`test/schema.test.mjs`（真实 fixture 过 zod）+ `test/migrations.test.mjs`，跑法 `node --test test/*.test.mjs`（node:test 内置，Node 24 直接 import `.ts`）。注意 `migrations.test.mjs` 断言了 `CURRENT_SCHEMA_VERSION===1` 且 `MIGRATIONS==={}`，升版时这两条必然失败，需同步改。
13. `lib/validation/engine.ts:226` 有一份**本地重复实现**的 `extractConditionVars`（不支持括号、按单层 split），与 `lib/conditions.ts:115` 的导出版并存分叉（后者被 `branches/page.tsx:112` 使用）。
14. `lib/store/merge.ts:9` 的 `MERGE_SKIP_KEYS` 与 `lib/store/history.ts:78` 的 `REVERT_SKIP_KEYS` 都已包含 `schemaVersion`——对账与撤销都不会回退版本号，这一层不用动。
15. `saveProject` 对传入的每个 node 行无条件 `version+1`（`lib/db/projects.ts:228-274`）→ 任何"批量写回迁移"都会引发 N 行版本跳变、其他标签页 409 与 BroadcastChannel 冲突提示。

## 设计结论

### D1 引用的存储形态 → 方案 (a) 的修订版：「已解析引用层」+「原文串」并存，但是同一引用的两个状态

新增（全部 optional，纯附加）：

```ts
/** 变量引用：绑定态带 varId；name 始终存在，既是未绑定态的值，也是悬空时的墓碑标签 */
export interface VarRef { varId?: string; name: string }
export type CompareOp = '>=' | '<=' | '>' | '<' | '==' | '!='
export type CondNode =
  | { k: 'cmp'; ref: VarRef; op: CompareOp; value: string | number }
  | { k: 'and'; parts: CondNode[] }
  | { k: 'or';  parts: CondNode[] }
  | { k: 'raw'; text: string }        // 子式/整段无法解析，原文保留（承载 `AND`、自然语言等）
export type EffectItem =
  | { k: 'eff'; ref: VarRef; kind: 'inc' | 'dec' | 'set'; value: string | number }
  | { k: 'raw'; text: string }
```

挂载点：`Choice.cond?: CondNode | null`、`Choice.effects?: EffectItem[]`、
`DialogueLine.speakerId?: string`、`SystemFunction.readIds?/writeIds?: string[]`、
`Ending.cond?: CondNode | null`、`EndingCondition.variableId?: string`。

**不变量**：AST 是机器真源（求值 / 数值分析 / Ink 导出只读 AST）；原文串是人机通道
（作者输入、AI 读写、未解析兜底）。写入必经单一闸口 `lib/refs/bind.ts`，禁止任何调用方
单独写其中一边。

理由：`conditions` 支持括号与 `&&`/`||` 混合嵌套，**扁平 `{varId,op,value}[]` 表达不了 `(a||b)&&c`**，
迁移时会静默丢语义 → 必须是树。而原文串不能删：AI 只认名字串（事实 5），且存量数据里绝大多数引用
根本解析不出来（事实 10），原文串就是"未解析态"的唯一载体。

被否决：
- **(b) 串里放 `{id}` 占位**——串仍是真源，作者与 AI 都写不出也读不懂 id 串，且对 `speaker` 完全无解。
- **(c) 只加 id、表达式仍按名字、求值时映射**——预览 `varState` 以 name 为 key（`preview/page.tsx:66,139-141`），同名变量在这一层必然合并，根因原地不动。
- **(d) 不做 id，改为强制变量/角色名全局唯一**——成本最低但已被事实 8 证伪（字符串改名连右值一起改），且存量近重名（事实 11）无法自动归一。**但唯一性约束应作为期 0 的附带件加上**：它让迁移解析变确定，是 id 化的前置条件，不是替代品。

### D2 AI 通道 → 契约完全不动；名字→id 的解析发生在客户端「采纳」边界

- 解析层：`lib/refs/resolve.ts` 纯函数。归一化顺序：trim → NFKC → 折叠内部空白 → 剥首尾引号/装饰括号；变量名按 ASCII 大小写不敏感（`conditions.ts` 的标识符正则本就限 ASCII），角色名按 NFKC + 去标点比对。
- 命中 0 个：
  - **变量 → 自动登记**。沿用已上线行为（`useBranchGeneration.ts:242-276` `registerOrphanVariables`），改为创建后立即回填 `VarRef.varId`，并在采纳面板列出「本次新登记 N 个变量」。变量是一行声明，自动创建的代价远小于留悬空引用。
  - **角色 → 绝不自动创建**。角色带 wound/lie/want/need/voiceProfile，自动建骨架会污染阵容与 world 审查；事实 11 就是反例（自动创建会多出第 5 个角色）。保持 `speaker` 文本 + `speakerId` 缺省，校验层聚合报 `UNBOUND_SPEAKER`，工坊 speaker 控件给「绑定到…/新建角色」。
- 命中 >1 个（同名）：不猜，留未绑定并报 `AMBIGUOUS_VARIABLE_REF`；采纳面板给下拉让人选。
- 归一化后唯一近似命中：在采纳面板作为**预勾选建议**呈现，绝不静默绑定。
- **放在客户端采纳时，不在服务端 route**。理由：(i) `/api/ai` 只拿到请求里的 `context`，没有权威项目态；(ii) store 里有未落库编辑，服务端 DB 副本更旧，按旧变量表解析会产出错 id；(iii) 采纳点是唯一能把「新登记 / 待确认」摊给人看的地方。先例见事实 6。
- **不新建统一采纳入口**（三条链路各写一套，统一会变成另一次大重构）。改为三处各加一行，调用同一个纯函数 `bindRefsInNodes(project, nodes)`。

### D3 迁移 → schemaVersion 1→2，纯附加，惰性跑在既有漏斗，不做批量写回

- 注册 `MIGRATIONS[1]`：遍历 `nodes[].choices`（conditions/variableEffects）、`nodes[].dialogue`（speaker）、`nodes[].systemFunction`、`endings`（conditions/variableConditions），用文档自带的 `variables`/`characters` 解析，产出 AST/id 字段，**不动任何原文串**。
- 歧义处理：精确名匹配 → 归一化后唯一匹配 → 否则留 `{name}` 未绑定。**同名（>1 命中）一律不猜**，留未绑定 + `AMBIGUOUS_VARIABLE_REF`（warning）。这就是"歧义无法自动解决 → 保留名字、打标待人工"的落点。
- 跑在哪：**四个 `migrateProject` 调用点一个都不用新增**（事实 4）——这是本次迁移近乎零风险的关键。
- **不做批量写回**：`saveProject` 会给每个 node 行无条件 `version+1`（事实 15），强制写回 = 未被请求的写风暴 + 多标签 409。迁移幂等，每次读都得到 v2，DB 里留 v1 无害；作者下次编辑该节点时自然写回。
- 顺序守卫：迁移在 `fromRows` 内、`ProjectSchema.parse` 之前完成，而 `mergeWindowEdits` 消费的是 GET 已返回的对象 → 两侧都是 v2，不会出现 v1 DB 节点覆盖 v2 本地节点。**这一条须用脚本断言**（期 1 V3）。
- 回滚：期 1–2 的 id 层**可从原文串完整重新推导**（迁移是纯函数，输入就是串 + 名单）。回滚 = 回代码；旧构建的 `ProjectSchema.parse` 会 strip 未知字段并在下次写入抹掉 id 层，但那是**可再生的缓存**，向前滚时重跑迁移即可。**期 3 起原文串降级，id 层不再可再生 → 期 3 上线前必须 `pg_dump` 快照**（写成闸门，见期 3）。

### D4 展示层 → 全站走 `refLabel`；悬空语义拆成三码；说话人问题必须聚合

- 名字跟随：展示一律 `refLabel(project, ref)` = `ref.varId ? (命中 ? 变量.name : «已删除：{ref.name}») : ref.name`。改名后引用自动跟随，因为没人再把名字当真源。
- 原 `UNKNOWN_VARIABLE_REF` 一码承担全部语义，必须分裂：

| 新 code | level | 触发 | 修法 |
|---|---|---|---|
| `UNRESOLVED_VARIABLE_REF` | warning | 只有 name、从未绑定（AI 新写 / 迁移没匹配上） | 「登记为变量」一键 |
| `AMBIGUOUS_VARIABLE_REF` | warning | 归一化后命中 >1 个同名变量 | 下拉指定 |
| `DANGLING_VARIABLE_REF` | **error** | 有 varId 但变量表里查不到 | 重新绑定 / 清除引用 |

`DANGLING` 比 `UNRESOLVED` 严重一档：作者曾显式绑过又把目标弄丢了。
- 说话人：`UNBOUND_SPEAKER`，**info 级且按项目聚合成一条**。依据事实 10——261 行对白 / 20 个说话人全部未绑定，逐行报会凭空加 261 条 issue，按 warning −8 分直接把 `passRate` 砸到 0，报告失去信号。
- **删除守卫不是重点**：`removeVariable` 今天不存在（事实 9），`DANGLING` 的现实成因只有 `setVariables` 整表换 id（事实 7）。要补的是让 `setVariables`/`setCharacters` 按归一化名字对账保留既有 id（期 0）。日后若加删除变量按钮，沿用 `world/CharacterCard.tsx:58-66` 已有的「（N 处引用）」二次确认样式。

### D5 Ink 导出 → 两跳保留，但 `inkVarName` 的缓存/去重键从「名字」改成「varId」

现状 `lib/persistence.ts:667-682` 按原名缓存 + `usedVarNames` 冲突加 `_2` 后缀。
**同名两个变量今天会共享同一个 Ink 标识符 → 在 Ink 里合并成一个变量**（同名不可分的下游症状）。
改为按 `ref.varId ?? '#' + normalize(ref.name)` 键化后：`trust`(id=A) → `trust`，`trust`(id=B) → `trust_2`，
语义分开。`VAR` 声明改为遍历 `project.variables` 按 id 产出；`applyInkEffects` / `conditionsToInk` 改吃
`EffectItem[]` / `CondNode`，每个 ref 走 `inkVarNameOf(ref)`。`persistence.ts:704-740` 那段「按引用补齐
未登记变量」保留，但输入从正则扫串改为扫 AST 里的未绑定 ref。
`speaker` 在 Ink 里只是文本行（`persistence.ts:771-774`），不经标识符化 → 期 2 只把它改成 `refLabel` 取名。

### D6 分期 → 期 0 前置修复 / 期 1 参照层+双写 / 期 2 读路径切 AST / 期 3 授权面+拆止血方案
